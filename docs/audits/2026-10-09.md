## A1. Auditoría de migraciones SQL, RLS y RPC (paso 1)

**Archivos:** [Foundation](https://github.com/ShadowStudioEnterprise/dayflow/blob/a9f5d460964a79c5c84ab30ea94505a141a863c2/supabase/migrations/202609200001_foundation.sql), [recurrencia](https://github.com/ShadowStudioEnterprise/dayflow/blob/a9f5d460964a79c5c84ab30ea94505a141a863c2/supabase/migrations/202609200002_task_recurrence.sql), [zona de recordatorios](https://github.com/ShadowStudioEnterprise/dayflow/blob/a9f5d460964a79c5c84ab30ea94505a141a863c2/supabase/migrations/202609240003_reminder_timezone.sql), [sincronización](https://github.com/ShadowStudioEnterprise/dayflow/blob/a9f5d460964a79c5c84ab30ea94505a141a863c2/supabase/migrations/202609240004_sync.sql), [Web Push](https://github.com/ShadowStudioEnterprise/dayflow/blob/a9f5d460964a79c5c84ab30ea94505a141a863c2/supabase/migrations/202610040005_web_push.sql).

### Hallazgos comprobados (C)

- Foundation declara RLS por `auth.uid() = user_id` en las tablas privadas y políticas para lectura/escritura inicial; la migración de sincronización revoca `INSERT/UPDATE` directos de entidades sincronizadas a `anon` y `authenticated` y exige mutación por RPC.
- `dayflow_apply_operation(jsonb)` comprueba identidad, propietario, entidad permitida, tamaño máximo de 2 MiB, idempotencia por ID, sellos y límite de reloj futuro de cinco minutos. Usa bloqueo transaccional por cuenta y emite acuse; `dayflow_pull` pagina historial exclusivamente para `auth.uid()`.
- Las funciones privilegiadas principales usan `SECURITY DEFINER SET search_path = ''`. `dayflow_register_push` valida propietario y proveedor HTTPS admitido y limita diez suscripciones por cuenta. Las RPC `dayflow_push_candidates` y `dayflow_claim_push` solo conceden ejecución a `service_role` según la migración.
- Las relaciones compuestas incorporan el propietario para reducir enlaces entre cuentas. El rol cliente no dispone de `DELETE` ordinario sobre las entidades sincronizadas; los borrados lógicos se representan con tombstones.

### Riesgos y verificaciones

| ID     | Prioridad                     | Evidencia | Observación / recomendación                                                                                                                                                                                 |
| ------ | ----------------------------- | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SQL-01 | Media                         | C/H       | Parte de los sellos de versión y fechas se recibe del cliente. Estudiar reloj lógico/versión autoritativa para minimizar conflicto entre dispositivos propios; no es una escalada entre cuentas demostrada. |
| SQL-02 | Media                         | C/H       | El orden LWW depende de fechas cliente; el límite de 5 min no elimina todo desfase. Mantener copias de conflicto y pruebas de convergencia.                                                                 |
| SQL-03 | Baja–media                    | C/H       | `endpoint` Push es único globalmente y el error de cuenta ajena puede funcionar como oráculo de existencia si se conoce el endpoint exacto. Unificar mensajes externos sin debilitar unicidad.              |
| SQL-04 | Baja                          | C         | Algunos validadores/funciones trigger no muestran `REVOKE EXECUTE FROM PUBLIC` explícito. Auditar privilegios efectivos y endurecer cuando proceda.                                                         |
| SQL-05 | Alta para cierre de auditoría | P         | Falta contrastar catálogo real de Supabase (`pg_policies`, `pg_proc`, `has_function_privilege`) y probar JWT de dos cuentas de ensayo.                                                                      |
| SQL-06 | Media                         | C/H       | Diez suscripciones por cuenta no equivalen a rate limiting. Estudiar límites de invocación y métricas de abuso.                                                                                             |

**Pruebas adversariales pendientes (P):** lectura y mutación cruzada A→B; `dayflow_pull` anónimo; acceso de `authenticated` a candidatos/claims Push; escritura directa en `sync_changes`; operación repetida con mismo ID y distinta carga; entidad no permitida; vínculos entre cuentas; carreras, fallos y cursores.

**Consulta de solo lectura propuesta** (debe ejecutarse en un proyecto autorizado, no desde el frontend):

```sql
select n.nspname, p.proname, pg_get_function_identity_arguments(p.oid) as args,
       p.prosecdef as security_definer, p.proconfig,
       has_function_privilege('anon',p.oid,'EXECUTE') as anon_execute,
       has_function_privilege('authenticated',p.oid,'EXECUTE') as authenticated_execute,
       has_function_privilege('service_role',p.oid,'EXECUTE') as service_execute
from pg_proc p join pg_namespace n on n.oid=p.pronamespace
where n.nspname='public' and p.proname like 'dayflow_%'
order by p.proname;
```

## A5. Política formal de notificaciones (paso 5)

### Contrato de producto

Dayflow **no garantiza alarmas críticas ni entrega exacta universal**. Guardar un recordatorio, sincronizarlo, programarlo, lograr aceptación por un proveedor Push y mostrar el aviso son estados diferentes, con evidencias distintas.

**Web/PWA:** Web Push suscrito voluntariamente, Supabase Cron revisa candidaturas aproximadamente cada minuto, y el proveedor/sistema/navegador determinan la entrega. La ventana documentada de recuperación y el TTL de mensajes es de cinco minutos. Se registra aceptación por proveedor, no visualización del usuario; pueden existir reintentos o avisos fuera de hora. Mensaje Push genérico sin información privada. Con Chrome completamente terminado en el Windows examinado, los avisos no llegaron a tiempo y se recibieron al reabrir; **no se soluciona exclusivamente con cambios frontend**. No existe un receptor nativo Windows en Dayflow 0.9.0.

**Android/iOS nativos:** Capacitor Local Notifications con permisos y validación de programación del sistema; límite conservador de 60 avisos próximos en 366 días; reprogramación cuando la aplicación está activa o se reanuda. Restricciones por Doze, batería, permisos, detención forzosa, reinicio y fabricantes. La programación pendiente no es prueba de entrega, y los escenarios físicos siguen pendientes.

**Sincronización y desactivación:** cambios offline no llegan al emisor web hasta sincronizar; una notificación ya aceptada puede no revocarse remotamente. La baja de suscripción local y limpieza por cuenta minimizan avisos de la cuenta anterior. En nativo, la cancelación y reconstrucción preservan identificadores para recuperación de errores parciales.

### Matriz formal de garantías

| Estado                        | Qué certifica                              | Qué NO certifica                 |
| ----------------------------- | ------------------------------------------ | -------------------------------- |
| `local_saved`                 | Dato confirmado en IndexedDB               | Presencia remota o entrega       |
| `remote_synced`               | Operación confirmada y pull completado     | Programación de aviso            |
| `native_scheduled`            | Identificador pendiente observado en el SO | Recepción puntual                |
| `push_submitted`              | Emisor ha intentado enviar                 | Aceptación del proveedor         |
| `provider_accepted`           | Proveedor aceptó solicitud                 | Presentación en pantalla         |
| `displayed` (futuro)          | Cliente confirma intento de mostrar        | Que el usuario lo vio            |
| `interacted` (futuro)         | Acción del usuario observada               | Lectura consciente del contenido |
| `failed` / `expired` (futuro) | Incidencia detectada                       | Recuperación garantizada         |

Los estados marcados _futuro_ son recomendaciones de instrumentación, **no** funciones existentes.

- Declarar explícitamente que las notificaciones críticas necesitan otro mecanismo independiente; no extrapolar del emulador o del proveedor Push a entrega real.
