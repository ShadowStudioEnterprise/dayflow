## Compatibilidad web objetivo

La compilación de Dayflow apunta a Safari 16.4 o posterior en macOS y Safari/PWA desde iOS y iPadOS 16.4. Para Android con Capacitor, el objetivo es Android System WebView basado en Chromium 111 o posterior. Son mínimos técnicos para la candidata, derivados de la compilación de Vite 8 y del CSS de Tailwind 4. La evidencia del APK histórico en WebView 97 sigue circunscrita a esa versión. [Objetivos de Vite 8](https://v8.vite.dev/config/build-options.html#build-target) · [Compatibilidad de Tailwind 4](https://tailwindcss.com/docs/compatibility#browser-support).

El recorrido automatizado de navegación, teclado y formularios usa WebKit de Playwright con perfiles de escritorio y móvil. Ejecuta `npx playwright install webkit` si falta el navegador y luego `npx playwright test --config playwright.webkit.config.ts`. La validación física requiere Safari y, para IOS-06, una transición A → B en la PWA instalada en el mismo origen. Registra las dos compilaciones, el worker de cada una y la conservación de sesión, datos y borrador. [Matriz de iPhone](audits/2026-11-18-pwa-ios.md).

## QA-06: Compilación Android release firmada

La firma la realiza el propietario en Windows con Android Studio, JDK 21 y Android SDK 36. La validación de QA-04 se hizo con una APK **debug** (0.9.0, código 1, `dd4ac54`); no acredita la compilación ni la instalación de la candidata firmada.

Usa una versión de Android Studio compatible con AGP 8.13.0, como Narwhal 3 Feature Drop (2025.1.3) o una versión estable más reciente que figure como compatible. Si el IDE indica que admite hasta AGP 8.6.0, actualiza Android Studio y conserva la versión de AGP del proyecto. Android SDK 36 requiere AGP 8.9.1 como mínimo. [Tabla oficial de compatibilidad](https://developer.android.com/build/releases/about-agp).

1. Parte del commit elegido y registra su SHA. Confirma que el módulo `app` usa `com.dayflow.app` y que `versionCode` es superior al de cualquier versión que la candidata deba actualizar. El proyecto parte de 0.9.0 (código 1). Usa la configuración pública de Supabase del entorno de distribución y excluye la variante Dayflow Local. Con las dependencias del repositorio ya instaladas, ejecuta desde la raíz:

   ```powershell
   npm run build
   npm exec -- cap sync android
   npm run native:android
   ```

   Continúa solo si cada comando termina correctamente. La sincronización se limita a Android y copia el frontend recién compilado al proyecto nativo.

2. En Android Studio, abre **Build → Generate Signed Bundle / APK**. Elige **Android App Bundle** para Google Play o **APK** para instalación directa. Selecciona el módulo `app` y la variante `release`. Usa la clave de subida registrada si la app ya usa Play App Signing, o la clave de firma correspondiente si distribuyes APK directamente. Crea una clave solo si aún no existe una que debas conservar. Guarda la keystore y su copia de seguridad fuera del repositorio. Introduce las contraseñas solo en el asistente, sin guardarlas en Gradle ni compartirlas.

3. Localiza el archivo generado. Para APK, usa `apksigner` de Android SDK Build Tools; para AAB, usa `jarsigner` del JDK. En los ejemplos, ejecuta solo el bloque correspondiente y sustituye la ruta por la del artefacto:

   ```powershell
   apksigner verify --verbose --print-certs "ruta\a\dayflow-release.apk"
   Get-FileHash -Algorithm SHA256 -LiteralPath "ruta\a\dayflow-release.apk"
   ```

   ```powershell
   jarsigner -verify -verbose -certs "ruta\a\dayflow-release.aab"
   keytool -printcert -jarfile "ruta\a\dayflow-release.aab"
   Get-FileHash -Algorithm SHA256 -LiteralPath "ruta\a\dayflow-release.aab"
   ```

   Confirma que la verificación es satisfactoria y que la huella SHA-256 del certificado coincide con la esperada. El hash del archivo identifica el artefacto y se registra por separado. Inspecciona el manifiesto con APK Analyzer para confirmar el paquete, la versión, el código de versión y que no sea depurable.

4. Para verificar la candidata, prueba el APK en un dispositivo de ensayo o usa un canal interno autorizado de Google Play para el AAB. Una APK release con un certificado distinto no puede actualizar la APK debug del mismo paquete. Si el teléfono ya tiene esa APK debug, usa otro dispositivo o perfil de pruebas para preservar sus datos. Con Play App Signing, verifica el certificado de distribución de Play para evaluar una actualización; el certificado del AAB corresponde a la clave de subida. Repite en la candidata los recorridos de QA-04 que correspondan, incluyendo arranque offline, persistencia de la cola y sincronización al reconectar.

Registra el SHA de Git, el tipo de artefacto, paquete, versión, código, SHA-256 del archivo y huella pública del certificado. Separa los resultados de compilación y firma, instalación y prueba física.

**Validación parcial · 19/11/2026, Europe/Madrid.** Se inspeccionó la release `com.dayflow.app` 0.9.0 (código 1) del [resultado de QA-06](#resultado-de-qa-06). `apksigner` verificó la firma v2 con el mismo certificado de QA-06 y `aapt` confirmó el paquete, la versión y la ausencia de `application-debuggable`. Para reproducirlo, calcula el SHA-256 de cada archivo, ordena por ruta relativa a `assets/public/` con comparación ordinal y construye líneas UTF-8 de `hash-en-minúsculas`, dos espacios y `ruta`, terminadas en LF, incluida la última. Los 73 archivos del `dist/` inspeccionado coincidieron byte a byte; la APK incluye además `cordova.js` y `cordova_plugins.js`. De los 75 archivos, 44 coinciden con los de la APK debug de QA-04. `bac619b` identifica el checkout de preparación de QA-06. El commit exacto que originó el frontend empaquetado sigue sin identificar.

Las horas y los retrasos de emisión se obtuvieron del reloj del teléfono y de `notification_enqueue` en Logcat. La recepción comunicada por el propietario tiene precisión de minuto.

1. Abre `/auth/register` en la URL publicada. Crea la cuenta de prueba con el correo acordado y una contraseña propia de al menos 12 caracteres.

## Web Push con la aplicación cerrada

Resultado del 4 de octubre de 2026: tras ajustar la hora del recordatorio, el usuario confirmó la recepción en Chrome. Supabase registra una entrega para las 12:32:00 Europe/Madrid, aceptada por el proveedor a las 12:32:00.576. Esa diferencia mide aceptación del proveedor, no llegada a la pantalla. La prueba solicitada consistía en cerrar las pestañas de Dayflow dejando Chrome abierto; el usuario confirmó la notificación, sin detallar por separado el estado de las ventanas. No acredita cierre completo del navegador, suspensión del sistema, Safari ni aplicaciones nativas.

Comprobación posterior: el usuario precisó que en **Windows, al cerrar todas las ventanas de Chrome, no recibe el aviso hasta volver a abrir Chrome**. Ese caso queda **fallido para entrega al vencimiento**, con recepción diferida confirmada. Los avisos de las 12:40 y 12:42 Europe/Madrid fueron aceptados por el proveedor a las 12:40:01.086 y 12:42:00.523, con un intento cada uno. No se ha inspeccionado si quedó un proceso Chrome activo ni su configuración de segundo plano. La hipótesis es que Chrome deja de ejecutarse al cerrar sus ventanas; debe comprobarse antes de atribuirlo definitivamente a una opción concreta.

El usuario indicó después que la opción de ejecución en segundo plano **ya estaba activada**. Por tanto, no se atribuye el fallo a una opción desactivada. La inspección local encontró Chrome 154.0.8037.93, 15 procesos y una ventana visible, sin un valor explícito de la política `BackgroundModeEnabled` en HKCU/HKLM. Esto describe el estado con Chrome abierto, no el estado durante el fallo; se solicitó cerrar las ventanas para comparar los procesos y confirmar que se prueba en este mismo ordenador.

Tras confirmar el usuario «cerrado», la consulta local devolvió **cero procesos Chrome y cero ventanas**. Queda comprobado que Chrome termina por completo en este equipo, aunque la opción de segundo plano figure activa según el usuario. La web no dispone de un proceso receptor en ese estado; mantener una ventana minimizada permite conservar el navegador en ejecución. La recepción independiente de Chrome requeriría otra integración con el sistema, que Dayflow no tiene implementada para Windows. No se han cambiado preferencias ni instalado componentes para forzar la persistencia del navegador.

Haz la prueba primero desde un navegador habitual que permita notificaciones, sin modo privado. En iPhone/iPad utiliza la PWA instalada. Registra el navegador, versión, sistema, si está instalada, permisos, modo de concentración, ahorro de energía y conectividad.

1. Inicia sesión, activa **Configuración → Activar avisos web** y confirma que el estado queda activo.
2. Crea un recordatorio a tres minutos vista con avisos activados; espera a «Sincronizado · 0 operaciones pendientes».
3. Cierra todas las pestañas/ventanas de Dayflow. Anota por separado si el navegador sigue ejecutándose, si se cerró por completo o si el sistema se suspendió. No son estados equivalentes.
4. Comprueba y registra hora efectiva del aviso, retraso respecto al instante previsto, ausencia de contenido privado y apertura del recordatorio al pulsarlo.
5. Repite con una recurrencia diaria; después modifica o elimina una ocurrencia futura y espera su sincronización antes de cerrar.
6. Desactiva los avisos y, en otra ronda, cierra sesión antes del vencimiento. No deben llegar avisos de esa suscripción; prueba también el cambio de cuenta.
7. Registra por separado desconexión breve, reconexión, suspensión del sistema y cierre completo del navegador. La ventana de recuperación del emisor es de cinco minutos; no se promete entrega indefinida ni exacta.
